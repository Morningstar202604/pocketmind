## 一、结论

本轮是**收尾审计**：不做架构级重构，只找「有具体证据、能实际修掉」的缺陷，
并把文档、版本、治理文件对齐到现状。共修 8 个真实缺陷，其中 2 个会造成
用户可见的数据/信任问题：

| 级别 | 问题 | 影响 | 状态 |
|---|---|---|---|
| P1 | `/api/export` 只导一页会话 | 第 501 个会话起静默丢失；"完整备份"承诺不成立 | 已修 + p27（8 断言） |
| P1 | `set_volume` / `set_brightness` 不校验退出码 | termux-api 失败仍报「已完成」 | 已修 + p26 |
| P1 | `read_url` 标 `safe` | 与 `web_search` 同为外发行为却免审批，被注入页面可静默外发本机 URL | 已修 + p26 |
| P2 | `normalize_path` 泄露消息主键 | 指标基数随消息数线性增长，用户数据 id 进入监控 | 已修 + p26 |
| P2 | `record_llm` 无调用方 | `/api/metrics` 的 LLM 指标恒为 0（假指标） | 已修 + p26 间接覆盖 |
| P2 | `run_agent_for_job` 手写 run 记录 | 缺 `cancelled`，取消失效依赖默认值 | 已修 + p26 |
| P2 | `/api/diagnostics` 同步阻塞事件循环 | 实测 0.58s 内所有 SSE/请求停摆 | 已修 |
| P3 | 前端 11px / 34px 违反自有硬约束 | 320px 视口下 8 个 E2E 用例全红 | 已修（12px / 36px） |

## 二、怎么发现的

### 2.1 基线

```text
$ bash tests/run_all.sh
通过 37 / 跳过 0 / 失败 0      # 改动前
```

37 项全绿，说明**门禁本身存在覆盖盲区**——下面这些问题全部在绿灯下存在。

### 2.2 逐个复现

**导出截断**：`Store.export_bundle` 的实现是
`list_sessions(limit=max_sessions)` 后直接返回，`max_sessions` 既是"上限"又被当成
"一页"。构造 5 个会话、`page_size=2` 时只返回 2 个（修复前）。

**写操作吞退出码**：`system.py` 的 `set_volume` 用裸 `_run()` 且丢弃 `code`。
用桩把 `_run` 返回值改成 `(1, "", "permission denied")`，函数仍返回
`{"ok": True, ...}`。

**指标泄露 id**：
```python
normalize_path("/api/sessions/abc/messages/987654")
# 修复前 -> /api/sessions/{id}/messages/987654
```

**事件循环阻塞**：`TestClient` 调 `/api/diagnostics` 实测 0.58s（本机、mock、
无外网超时），期间同一进程的其它请求排队。

## 三、修复要点与验收

| 缺陷 | 改法 | 验收 |
|---|---|---|
| 导出截断 | `export_bundle` 按 `page_size` 翻页取尽，`max_sessions` 改为总量上限；`list_sessions` 增加 `offset` 与稳定排序 `updated_at, id` | `p27` 8/8；`p25` 12/12（查询数仍 ≤6/页） |
| 写操作退出码 | `set_volume` 走 `_run_checked`；`set_brightness` 显式判 `code != 0` | `p26` 4 条（失败/成功各 2） |
| read_url 分级 | `risk="write"`，与 `web_search` 一致 | `p26` 2 条 |
| 指标 id | `normalize_path` 对 `messages/<digits>` 归一化 | `p26` 3 条 |
| LLM 指标 | `Agent._stream_round` 计时并 `record_llm` | `p26`；`/api/metrics` 实测非 0 |
| job run 记录 | 改用 `_new_run()` | `p26` 2 条 |
| diagnostics 阻塞 | `asyncio.to_thread(run_diagnostics, ...)` | `p14` 端点断言 + 手工计时 |
| 前端硬约束 | 11px→12px（`.caps-chev`/`.risk-tag`/`.conn-pill`）、34px→36px（窄屏 icon-btn） | `mobile.spec.ts` 8/8 视口 |

## 四、没有做的事（以及为什么）

| 项 | 决定 | 理由 |
|---|---|---|
| 拆 `create_app`（1100 行闭包） | 不做 | 可测性痛点已由 p14 的 TestClient 解决；93 处闭包引用、43 个路由全在启动路径上，风险 >> 收益。验收标准写在上一份报告 |
| 拆 `Store`（953 行） | 不做 | 8 个功能段但只有 2 个成员被外部依赖；抽出的收益是行数，代价是 3 个调用方约 20 处改动 |
| 引入 SonarQube / 技术债比率 | 不做 | 单机项目引入服务端工具不划算；用 radon MI + 变异测试替代 |
| 消息列表虚拟化 | 不做 | 单会话实测 ≤200 条时渲染 < 16ms；虚拟化会引入滚动锚定复杂度 |
| 并行子代理 | 不做 | 与"审批串行确认"的安全模型冲突，需要先设计并发审批队列 |

## 五、剩余风险

1. **行覆盖率仍低于 90% 红线**（上轮实测 59%）。本轮新增 22 条断言，
   但集中在工具层与导出；`main.py` 的路由错误分支仍是主要缺口。
   验证方法：`python -m coverage run --branch -m pytest`（需先装 dev 依赖）。
2. **真机未验证**：所有 E2E 在 Chromium + Windows 完成；aarch64 真机的
   termux-api 行为（短信/定位/传感器）只有模拟器证据。
3. **`mypy` 未进门禁**：`agentd/` 仍有 95 条 `Store | None` 收窄告警，
   属于架构性（模块级单例在 lifespan 后才赋值），修它需要引入应用状态对象，
   与"不拆 create_app"的决定冲突。当前以 ruff + compileall + 单测为准。
4. **提示注入**：仍然是设计上的固有风险，靠审批门而非内容过滤缓解。
